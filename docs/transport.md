# Stream transport and request failures

Handlers return ordinary Effect Streams. Sewed divides their encoded batches into ordered RPC messages that fit the 256 KiB limit. A forwarding handler can map an incoming client stream directly; it does not need to know the transport's chunk size.

For ordinary protocols, the limit counts UTF-8 bytes after JSON encoding, including the envelope, request ID, punctuation and escaping. Each individual value must fit with its envelope. Sewed does not divide a string or object into pieces or reassemble bulk objects on the receiver. Opt-in [binary protocols](binary-streams.md) count MessagePack bytes instead; `Binary.chunks` lazily divides a byte source into stream values before encoding.

JSON envelope checks avoid a temporary UTF-8 buffer when the text's UTF-16 length proves it fits: each code unit needs at most three UTF-8 bytes, including an unpaired surrogate. Near the limit they measure exact encoded bytes. Admission budgets and stream framing still count exact bytes; this shortcut changes neither the accepted messages nor their limits.

A request travelling the other way is framed only when its operation declares `Binary.bulk(rpc, { field, maxBytes })`. The client encodes that request once and sends slices of the encoded packet; the owner concatenates them and decodes the whole request, allowing the named field its declared bound and the rest of the request one envelope on top of it. Every other packet, including each individual slice, keeps the 256 KiB limit. A bulk operation requires a binary protocol, so its field crosses the wire as the bytes the transport measures rather than as base64 text. See [bulk requests](binary-streams.md#bulk-requests).

## Flow control and lifetime

Sewed sends one fragment of a split batch and waits for its acknowledgment before sending the next. The final fragment uses Effect RPC's normal acknowledgment, which controls when the handler can produce its next batch. Acknowledgments indicate admission to the client's bounded RPC queue; they do not mean application processing has completed.

A bulk request's slices follow the same discipline in the client's direction: one slice is in flight, and the owner acknowledges each one before the next is sent. The final slice carries no acknowledgment of its own, because the request's own response ends it. One bulk request is in flight per connection, so an owner holds at most one assembly; ordinary requests on that connection are sent between slices rather than behind them.

Each owner also admits at most 128 MiB of pending encoded request bytes across its connections. Partial transfers reserve bytes as they arrive; completed requests keep that reservation until their response ends or their connection closes. An exhausted budget answers `Limit` with `reason: "transport/pending-bytes-limit"` before the handler runs. Cancelling a partial transfer releases its reservation. A client connection applies the same 128 MiB aggregate budget to bulk answers until they are delivered or retired; exceeding it closes that connection with a `Limit` diagnosis. Already-sent calls report `Unknown` with that cause. These budgets measure encoded data retained by transport, not application allocations or total JavaScript heap usage.

Binary decoding compacts packets whose byte view covers only part of a backing buffer and snapshots shared backing storage. Retained byte fields therefore cannot keep an unrelated oversized buffer alive. An ordinary packet that already owns exactly its encoded bytes is decoded without that copy.

Payload schema decoding belongs to the admitted request's lifetime. A suspended asynchronous decoder leaves other requests and control messages usable. Interruption, disconnection, or owner shutdown cancels decoding before it can dispatch a handler. Queued requests keep their own admission identity, including when a peer immediately reuses a cancelled request ID.

Only the current intermediate acknowledgment is retained for each active request. Interruption or connection closure releases that wait and the handler's scope. Other requests keep their own lifetimes. No request is replayed and no owner is replaced. A bulk request interrupted or disconnected before its final slice leaves no assembly behind, and the one lost before delivery reports that in its failure rather than leaving it open.

Framing bounds individual outgoing messages. It does not bound the size of a batch constructed by an application or the memory needed by its schema codec. The JSON transport still copies values across the runtime boundary.

Renderer replies and connection-close notifications are routed to subscribers of their connection before crossing the preload's `contextBridge`. Unrelated idle bindings do not receive, copy or validate those packets. The selected renderer connection still validates each envelope and payload; document revocation and connection errors retain their existing lifetimes.

## Oversized values and defects

Deferred clients reuse one connection per slot by default. The first call on a slot starts building that connection in the runtime's own scope, and every call, the first included, waits for it: a caller interrupted mid-build, such as a React component unmounting mid-connect, stops waiting and the build carries on for the others, and a failed build answers every waiting call with its failure and lets the next call build again. The benchmark also measures the per-call alternative, whose extra renderer handshake dominates small calls. An oversized outgoing request fails locally with `SewedError` code `Limit`; on an operation declared bulk, the same happens against its declared field, and the message names that field and its bound. Transport failures reach callers as `SewedError`, with the Effect RPC client error retained as `cause`: `Closed` for a lost connection, `Limit` for an exceeded byte or queue limit, and `Protocol` otherwise. A request already in flight when the connection is lost answers typed too, both on the default shared connection and per-call: one still queued — the bytes never left, whether it is an ordinary request or a bulk one still sending parts — fails `Closed` with `reason: "transport/closed-before-send"`; one already sent, with no answer back, fails `Unknown` with `reason: "transport/lost-after-send"`, because whether the handler ran is genuinely unknown. Nothing retries either: a caller that retried on a bare interruption before must not retry an `Unknown`, since the handler may already have run. An oversized response value fails the affected request typed, not as a defect: `SewedError` code `Unknown`, `reason: "transport/answer-over-limit"` — the handler ran and its answer did not fit the envelope, so the caller must not retry it. A stream may have delivered earlier fragments before a later value fails the same way, and the stream's handler is interrupted, so its finalizers run. This typed failure needs an operation whose `error` schema admits `SewedError`: on one declared with no `error`, or with an error schema that excludes `SewedError`, the refusal cannot decode as the operation's error, and the caller reads `Protocol` with a message such as `<tag>: Expected never`, typed, on a connection that stays usable. Declare `error: SewedError` (alone or in a union) on an operation whose answer may exceed the envelope.

`SewedError.cause` retains the original diagnostic locally. When the error crosses a runtime boundary, its cause is encoded as JSON data. Native and Effect error objects carry their name, message and nested cause without a stack trace. Already structured diagnostics preserve their fields, including transport codes and reasons, when another owner forwards them. Forwarding operations must declare `SewedError` in their error schema.

Handler defects also stay with their request, including when a worker forwards a downstream failure. Sewed selects Effect RPC's request-scoped defect handling so a failed handler does not end unrelated requests on the same connection. Declared domain errors retain their protocol schema. The same client and owner can handle later valid calls.

A message that parses but does not decode stays with the request it names, too. On the client, an answer or a stream value that is not canonical MessagePack, or that parses but does not match its envelope, fails the one request whose `requestId` it carries with `SewedError` code `Protocol`, `reason: "transport/undecodable-answer"`, and the client tells the owner to stop that request, as an interruption would. The handler ran, so the caller must not retry it. On the owner, a request that parses and names an identity not already open on the connection, but does not decode, is answered with `Protocol`, `reason: "transport/undecodable-request"`: the handler did not run. A bulk request or bulk answer whose assembled packet does not decode fails its own request in the same way. The connection and every other call on it continue. Main's renderer bridge and a worker's dependency relay forward such a packet to the endpoint that fails it, rather than closing on it.

Request IDs preserve their wire type: the number `1` and the string `"1"` are different identities. Naming an active request by its other wire type is a protocol violation, reported at once in place of a call that would wait forever. A reply that does so fails that one call with `Protocol`. A mismatched acknowledgment, a bulk answer whose assembled reply does not carry its parts' own ID, or a request or control message the owner receives that way ends the affected connection. Terminal failure delivers typed errors before unsubscribing and closing the connection, including for direct `Binding.client` callers whose environment remains open.

A packet that does not parse at all, is not exactly one message, names no request the receiver is tracking, or names a request already running on the owner cannot be attributed. It ends the connection, and the requests open on it fail as for any lost connection. So does a bulk part, or a part's acknowledgment, that does not decode: both ends are still pacing that transfer, and ending the connection is what retires the assembly on both. Connection I/O failures also end the affected connection. These are different from a valid request whose handler returns an oversized value.

The implementation follows the [Effect RPC server's acknowledgment and defect contract](https://github.com/Effect-TS/effect/blob/main/packages/effect/src/rpc/RpcServer.ts). Tests withhold acknowledgments, interrupt waiting handlers, check exact byte boundaries, and deliver more fragments than the transport inbox can hold at once. The external playground's `pnpm benchmark:transport` exercises real workers, renderer IPC and worker dependencies, including escaped Unicode and failed requests sharing a client with successful work.
