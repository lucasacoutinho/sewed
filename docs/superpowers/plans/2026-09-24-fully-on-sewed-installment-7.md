## Rulings

1. **An answer over the envelope fails `Unknown` with `reason: "transport/answer-over-limit"`, typed, through the operation's error channel.** Today the owner's `send` (`Runtime.ts:137`) throws `Limit` synchronously and Effect's RPC server turns the throw into a per-request `Die` after the handler ran. The owner now catches that refusal for an `Exit` and sends a typed failure in its place — the same `failExit` shape the client uses for a lost connection — so the caller sees `SewedError { code: "Unknown", reason: "transport/answer-over-limit" }`: the host ran, its answer did not arrive, do not retry. `Unknown` rather than `Limit`, because `Unknown` is the code a caller already reads as "may have run". A stream's oversized value keeps today's per-value behaviour but becomes the same typed failure instead of a defect.
2. **`Binary.bulkAnswer(rpc, { maxBytes })` declares that an operation's success value may exceed one message.** Symmetric with `Binary.bulk`: an annotation on a unary operation in a `Binary.protocol` (a JSON protocol is refused where the capability is defined, `Protocol`, as the bulk request is; wrapping a group in `Binary.protocol` changes the encoding, not the types); a stream-shaped operation is refused at the annotation. The owner encodes the `Exit` once and, when it exceeds an envelope, sends slices of the encoded packet as answer parts (`{ id, bytes, final }`), one in flight, each acknowledged by the client before the next — backpressure from the renderer to main; the client assembles up to `maxBytes` plus one envelope, validates, decodes and completes the request. An answer over `maxBytes` is ruling 1's failure. A connection lost mid-answer is `Unknown` / `transport/lost-after-send`. `maxBytes` is a positive integer of at most 64 MiB, as `Binary.bulk`'s is. An in-process call has no bound.
3. **`keep` holds the native window title.** Electron keeps a window's title only when the BROWSER WINDOW's own `page-title-updated` is prevented; the contents' event has no such effect. `internal/Window.ts`'s window-level listener resolves `Decidables.WebContents.TitleUpdate` on the window's contents registry and prevents the event on `keep`; the contents-level `preventDefault` goes (it was inert). The title stream keeps following the page (installment 6). Probe on 44.3.0 first: a `setTitle("Fixed")` window loading a titled page keeps "Fixed" when the window-level event is prevented and not when only the contents' is.
