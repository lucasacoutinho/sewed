# Installment 8: JSON-Shaped Data Survives the Binary Wire, and One Bad Message Fails One Call

## Rulings

1. **Exact round-trip, at no cost on the ordinary path.** msgpackr (2.1.0) renames a decoded `"__proto__"` key to `"__proto_"` (reproduce first). `decodeBinary` keeps its fast path — the default unpack and the canonical re-encode check. Only when that check fails does it decode the same bytes again with maps preserved (`mapsAsObjects: false`, so maps arrive as `Map`) and rebuild each map as a plain object whose keys are all defined as own, enumerable, writable, configurable properties (`Object.defineProperty`, so `"__proto__"` is an own key and no prototype is ever set — exactly what `JSON.parse` yields), then runs the canonical check on the rebuilt value; a value that still fails is refused. Non-string map keys (a JSON-shaped value never has them) are refused rather than coerced. Verify the value then survives the RPC schema layer (a `Schema.Unknown` field, a `Schema.Record`, a struct) intact, as it does on the JSON protocol, and pin it.
2. **One undecodable message fails one call.** On the client, a server message that parses as MessagePack and carries a `requestId` the client is tracking, but fails the canonical check or the envelope schema, fails that request with `SewedError { code: "Protocol", reason: "transport/undecodable-answer" }` (typed, through `failExit`), and the connection continues; a packet that does not parse or names no tracked request still fails the connection, as today (it cannot be attributed, so it is a broken or hostile peer). On the owner, a request packet that parses and names a request id but fails decoding is answered with the same typed failure (`reason: "transport/undecodable-request"`) instead of disconnecting; a packet that cannot be attributed disconnects as today. Bulk parts: an assembled bulk request or bulk answer that fails decoding fails its own request the same way.
3. **Large messages use a throwaway packer and no redundant copy.** Above a threshold (measure; start at 1 MiB of encoded output, or when the shared packer's buffer would grow past a few MiB), `encodeBinary` packs with a fresh `Packr` whose output it owns, so no `Uint8Array.from` copy is needed and the shared buffer never grows; the canonical re-encode of a large decoded message uses the same throwaway packer. Where a copy is unavoidable (assembling parts), avoid a second one. Measure the peak per side for a 12 MiB and a 64 MiB bulk answer and a 12 MiB bulk request before and after (`process.memoryUsage()` / `performance.measureUserAgentSpecificMemory` where available, or heap snapshots in Node over `pair()`), and state the after numbers in `docs/binary-streams.md` as "a bulk message of N bytes peaks at about K×N on the sender and M×N on the receiver"; after the message, the shared packer's buffer is back to its ordinary size (assert it).
